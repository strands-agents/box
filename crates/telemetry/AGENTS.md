# AGENTS.md

Guidance for coding agents working on `crates/telemetry`. Follow
[repository guidance](../../AGENTS.md) first. `CLAUDE.md` symlinks to this file.

Decisions live in the
[Telemetry section of `docs/design/decisions.md`](../../docs/design/decisions.md#telemetry).

## Before you change this crate

- **The receiver is reachable by the workload, which is untrusted.** `axum` owns the HTTP framing.
  This crate's own parts are the three route walks, `strip_and_stamp_resource`, and the protobuf
  decode, so a change there needs a hostile-input test.
- **Two defects were found and fixed here before: an agent forging a permit record, and an agent
  flooding the queue to drop the box's own refusals.** Check a change against both.
- **The SDK flushes targets in sequence**, so N unreachable endpoints cost N export deadlines at
  teardown. That cost is not measured.
- **A box once hung for ever on exit, and the entry below records what closed it.** Read it before you
  touch `Drop` or `drained`.

## What this crate owns

| Concern | Owner |
|---|---|
| the OTLP schema | `opentelemetry-proto`, generated by the project |
| the queue, the batching and the flush | `opentelemetry_sdk`'s `BatchLogProcessor` |
| the HTTP server for the agent's port | `axum`, behind a one-permit decode bound |
| the OTLP mapping | `opentelemetry-proto`'s `group_logs_by_resource_and_scope` |
| encoding a payload | this crate, one mapping for both file and endpoint |
| the HTTP client | `reqwest`, at the same version the vendored shell declares |
| the receiver | this crate; the OpenTelemetry SDK emits and does not receive |
| the file format | this crate; `opentelemetry-stdout` writes a debug format, not the Collector's |

**The SDK owns the queue; this crate owns one `LogExporter`.** `TargetLane` is a thin `LogProcessor`
that filters by signal and wraps `BatchLogProcessor`, which carries the queue, the batching and the
bounded flush. Do not rebuild any of those here.

**`opentelemetry-otlp` is NOT adopted, and that is the one line to keep.** It requires
`reqwest 0.13.1` and the vendored `shell` declares `0.12`, so taking it puts two TLS stacks in the
process that holds the CA private key. The SDK itself needs no new package: `opentelemetry`,
`opentelemetry_sdk` and `tokio-stream` were already in `Cargo.lock`.

**The agent's spans do not go through the SDK, and cannot.** The SDK emits and never receives, and
`opentelemetry-proto` transforms only SDK types into proto. An agent span arrives already encoded, so
`TargetExporter::relay_trace` sends it directly. There is no `SdkTracerProvider`.

**`reqwest` is declared exactly as `shell` declares it** —
`{ version = "0.12", features = ["rustls-tls"], default-features = false }` — so feature unification
keeps one copy in the graph. Check `grep -c 'name = "reqwest"' Cargo.lock` stays at `1`.

## Findings and footguns that already cost something

- **An argument reaches the record when its word was LITERAL in the script, and otherwise only when it
  is a plain flag.** That is a security rule rather than a formatting one. The Shell holds
  arguments **post-expansion**, so `echo $(cat secret.txt)` puts the file's *contents* in the vector.
  Measured on a real box before the redaction: the value appeared twice in the record file, which a
  target may ship to a vendor endpoint with a credential attached. The
  [fixed attribute set](../../docs/design/decisions.md#the-policy-attribute-names-are-this-products-own)
  excludes `process.command_line` for exactly this reason.
  **Shape alone was tried first and was useless.** Shape plus `plain_flag` redacted 94 values in one
  `cc-demo` run, nearly all of them shell keywords, zsh
  option names, and **closing brackets**. `pipefail` and `hunter2` are the same shape, so no syntactic
  rule separates them. The provenance flag does: a literal word is already in a file the operator can
  read. The same demo run then reported 10 redactions instead of 94, each a genuinely expanded value,
  and `cat allowed.txt` and `[[ -r … ]]` came back whole.
  `reportable` is the gate for an EXPANDED argument, and it lives **in this crate** rather than in the
  enforcement point, so no caller can pass a raw vector by mistake. A missing mask entry counts as
  expanded, so a caller supplying none redacts rather than leaks.
  `a_literal_argument_is_reported_and_an_expanded_one_is_judged`,
  `an_absent_mask_entry_is_treated_as_expanded`,
  `an_expanded_argument_is_reported_only_when_it_is_a_plain_flag`,
  `a_prefix_cannot_carry_an_expanded_secret_into_the_record` and
  `a_secret_passed_as_an_argument_never_reaches_the_record` are the five pins.

  **`path_shaped` is DELETED, because one `/` defeated the whole gate.** It reported any expanded
  value opening with `/`, `~/`, `./`, or `../`, so `echo /$AWS_SECRET_ACCESS_KEY` wrote the key to the
  record verbatim. Measured on a real box: two 40-character keys over the AWS alphabet differing only
  in the first character, the bare one `<redacted>` and the `/`-prefixed one written in full, twice —
  which is exactly the pre-redaction measurement above. It needed **no permit**, because
  `decision_subject` attaches the same `Subject::process` to `gate_deny` as to `gate_permit`.
  **Do not reintroduce a shape test for an expanded value.** `/workspace` and a 40-character key
  opening with `/` are one shape, so no syntactic rule separates them — the same argument this entry
  already makes about `pipefail` and `hunter2`. A 2026-09-26 review proposed widening `path_shaped` to
  accept a bare relative name and was declined on that ground; the deletion is that ground carried to
  its conclusion.
  **The deletion costs no audit data.** Measured on a real box: for
  `zsh -c 'cat $PWD/allowed.txt'`, `process.command_args` now holds `<redacted>` while the same
  command's own `fs:read` decision still carries the full path under `file.path`. The path was
  recorded twice and is now recorded once, by the decision that authorized it. A LITERAL path is
  unaffected and still reported whole, which is why
  `box_telemetry.rs::a_shell_decision_states_its_arguments_and_its_directory` passes unchanged — the
  outer bash expands `$BOX_HOME` there, so the Shell receives a literal word.

  **`plain_flag` takes one letter after a single `-`, and a `--` name is lowercase and bounded.** The
  first version required only an alphanumeric first character and put no cap on the tail, so four
  shapes passed the gate and reached the record verbatim: `-deadbeef1234abcd`, `-lhunter2`, `-1abc`,
  and `-0000-0000-0000`. A short option carrying its own value is how a secret rides in, and no
  syntactic rule separates `-lhunter2` from `-la`. **So `-la` is redacted too**, which
  `an_expanded_argument_is_reported_only_when_it_is_a_plain_flag` states in its redacted list.
  That loses a little benign audit data and closes the leak; it costs nothing for a *literal* `-la`,
  which `Subject::process` reports unchanged without reaching this gate at all.
  **The `--` branch had the same defect one prefix along**: it capped nothing and allowed every
  alphanumeric, so `--$AWS_SECRET_ACCESS_KEY` reported the key as a flag name, and
  `--<secret>=x` reported it as a name with the value redacted. A name is now
  `MAXIMUM_FLAG_NAME_CHARS` or fewer characters of lowercase letters and dashes. **The residual is
  stated rather than closed**: a lowercase-only string of bounded length matches no common credential
  format — AWS keys are mixed case, hex and base64 tokens carry digits, JWTs carry dots — so this is
  an entropy argument about real formats and not a proof. It costs `--http2`, `--ipv6`, and
  `--base64` when those arrive *expanded*, which is rare, and nothing when they are literal.
- **A control-plane operation has no request to inherit a parent from, so the run supplies one.**
  `Collector` mints one `control_trace` and one `control_root` at `start`, and the run's FIRST control
  operation takes the root while every later one names it as parent. The alternative — a fresh root per
  operation — is four unrelated traces for one box life, which a viewer cannot assemble. The first
  operation is whichever one is emitted first, not `box_started` by name, because nothing here orders
  the box's own calls. `one_trace_holds_the_runs_whole_control_plane` pins the shape, and
  `a_control_operation_exports_a_span_beside_its_log_record` pins the pairing. Measured on a real box:
  one trace, `control box_started` as the root, `policy_installed`, `discovery_complete` and
  `box_stopped` beneath it.
- **`SPAN_OMITS` holds one key, and it was lost once before.** `box_spans` filters
  `strands.box.trace.parent_span_id` out of the span, because the span states it as `parentSpanId`.
  [A span omits what a span field states](../../docs/design/decisions.md#a-span-omits-what-a-span-field-states)
  owns why, and why nothing else is omitted.
  **Read the span's field BEFORE you filter.** `box_spans` builds `parent_span_id` from
  `record.attributes`, so filtering in place would empty the field it is meant to leave
  authoritative.
  **Two keys left the record entirely rather than joining this list.**
  `strands.box.trace.parent_sampled` and `strands.box.trace.state` are no longer emitted, by the
  re-introduction-cost rule in
  [emit only what a consumer reads today](../../docs/design/decisions.md#the-policy-attribute-names-are-this-products-own):
  neither was read by any code, and each is about two lines to restore. The box still **propagates** a
  caller's `tracestate` downstream, which `Correlation::apply_to` does from memory, so only the record
  changed. Six box and telemetry assertions now pin the inverse — a caller sends a `tracestate` and
  the span records none of it.
  **`caused_by` uses `assert!` rather than `debug_assert!`, deliberately.** A mislabelled security
  decision in an audit record is worse than a crash, so the guard fires in release too. Every call
  site in `box`'s `run/telemetry.rs` pairs a cause with a verdict it admits, so it cannot fire today.
  **This narrowing shipped on 2026-09-23 as `d5fd87c2` and then vanished**, because the span export was
  re-authored on the mainline-merge line and no span-export commit is an ancestor of the branch that
  held it. The branch is `backup/vvargu/otel-stiching-impl`, which GitHub never had. The mandatory
  `DecisionCause` went the same way. So neither is a new idea: both are a restoration, and the lesson
  is that a re-author loses what a rebase would have carried.
  Three test files asserted `span["attributes"] == log["attributes"]` and each had to change with the
  behaviour — `collector.rs`'s
  `decisions_export_spans_and_matching_logs_with_request_parentage`, plus the span/log helpers in
  `box/tests/box_credentials.rs` and `box/tests/runtime_mcp_policy_staging.rs`. Each now compares the
  two sets with the omitted key removed, and asserts the log record still carries it, so a filter
  that omits too much fails as loudly as one that omits nothing.
- **The remote-parent span flags belong to the policy plane alone.** `box_spans` set `0x300` —
  `has_is_remote_parent | is_remote_parent` — whenever a record carried
  `strands.box.trace.parent_span_id`. But the control plane adds that attribute for every non-root
  operation, naming this run's own `control_root`, which is local. So each control child exported
  `flags = 771` and a viewer drew the box's own children as if a remote caller had sent them. The
  gate is now a match on `Plane`, and `a_control_child_never_claims_a_remote_parent` pins it. Found
  by review on 2026-09-26.
- **`box_spans` admits a scope, so a new box scope is invisible to it until named.** It was
  `decision_spans` and it tested `scope.name != "strands-box.policy"`, so the control plane reached the
  file as a log and never as a span. A second gate hid it as well: `Collector::control` set no trace
  context, so even a widened scope test would have skipped every control record for want of a span ID.
  The scope test is now `Plane::of`, an exhaustive match on the two scope constants, and the constants
  are `pub(crate)` so the two files cannot drift on the spelling. The agent's own scopes fall through to
  `None` and relay untouched.
- **Severity is what routes a record to a lane, so two signals may never share one.** `TargetLane::emit`
  reads `Signal::of_severity` and nothing else — not the scope, not the attributes. So adding a signal
  means adding a severity no other signal holds; `control_plane` took `Info2`. Sharing one would file a
  control-plane record as a permit, silently. `no_two_signals_share_a_severity` is the pin.
- **The two planes share one destination, and a reader must select a scope.** Decisions carry
  `strands-box.policy` and control-plane records carry `strands-box.control`. Two box tests indexed
  `scopeLogs[0]` and broke the moment control records started arriving first — a box records that it
  started before it decides anything. A query over one file that does not name a scope will read the
  wrong record shape, and the shipped `jq` recipes had to gain a `select(.scope.name == …)` for that
  reason.
- **A record is only as good as the `drained` that carries it, and `drained` has ONE caller.**
  `Collector::drop` is the other route out of the queue and it waits for nothing, so a record
  queued on a path that reaches no `drained` is lost, not delayed. Measured: `policy_refused` and
  `box_started` both reached a **0-byte** file when the box refused its policy, because the refusal
  returned before any `HostedBox` existed and the drain lived inside one. The box now drains in
  `command::run::execute`, which is the one point every exit reaches.
  `a_run_that_fails_before_its_workload_still_records_its_stop` is the pin, and it fails when the
  teardown block is removed. **Do not move the drain back inside a type a failure path can skip.**
  This fixed the *drain*, and it decides nothing about routing: a target whose signal set omits
  `control_plane` still receives no control-plane record, because `Collector::control` returns at the
  acceptance union first. That is the operator's list working as
  [a target names a set of signals](../../docs/design/decisions.md#a-target-names-a-set-of-signals) says it should.
  An absent list takes **every** signal, and a list that is written must name `trace` to keep
  the control plane, because `trace` expands to both `agent_trace` and `control_plane`. The six
  spellings here are this crate's own; `box.toml` takes five words — `deny`, `permit`, `trace`,
  `logs`, `metrics` — and the box expands them.
- **`agent_logs` and `agent_metrics` are UNCONDITIONAL, and no list narrows them away.**
  `Collector::start` unions `Signal::always_received()` into every target's lane, by the maintainers'
  direction on 2026-09-29, so `include = ["deny"]` holds the refusals **and** the agent's own log
  records and metrics. The two words stay in `box.toml`'s vocabulary, and each now names what a
  target already holds.
  `a_target_naming_only_refusals_still_receives_the_agents_logs_and_metrics` is the pin, and it
  fails with an **empty** file when the `chain` is removed.
  **The union is in `start` rather than in `Target::receiving`, deliberately.** `validate` reads the
  authored `signals` field to refuse an empty list and a repeated signal, so storing the union would
  make both refusals unreachable. The `is_relayed` test at the end of the lane loop reads the
  authored list for the same reason: a target naming only relayed signals still gets no SDK log
  lane, because that worker would have nothing to do.
  **What this cost:** a narrowing target is no longer pure. The `telemetry-viewer` example held a
  `[telemetry.refusals]` file whose checks read "no agent payload of any shape is here", which this
  rule makes false; that target is **deleted** by the maintainers' direction, because a second file holding
  denials alone demonstrated narrowing rather than carrying a property. What still pins narrowing is
  `box_telemetry.rs` — `a_policy_denied_target_keeps_only_the_refusals`,
  `below_trace_an_agent_span_is_answered_and_discarded`, and
  `a_narrowed_target_still_receives_the_agents_own_logs_and_metrics`, which asserts in one test that
  the two relayed signals arrive and a span does not.
- **`Target` has TWO constructors and the default signal set must be in both.** `Target::new` and
  `Target::opened_file` each state their own set, and the box's *default* target — the one a box with
  no `[telemetry]` table gets — is built by `opened_file`, because `config_for` hands it an already
  open descriptor. Widening only `new` left `opened_file` on the two verdicts, so every
  control-plane record for a box that declared nothing was dropped at the acceptance union: the file
  came out **empty** of control records while `Signal::default_signals()` said otherwise, and every
  test of the default passed because each reached `new`.
  `an_opened_default_target_receives_the_control_plane` is the pin, and it names `opened_file`
  deliberately. When a signal joins the default set, grep for every `signals:` initializer rather
  than the function you happen to be reading.
- **An attribute's length is not the box's to choose, so `ControlRecord` bounds every one at
  construction.** A refusal reason is an MCP server's own schema diagnostic or a
  `PolicyStagingError::UnresolvedPolicies` list, and a 512 KiB reason produced one 525,417-byte JSON
  line. The bound is `MAXIMUM_ATTRIBUTE_BYTES`, applied inside `completed`, `refused` and `detailed`
  rather than at a call site — three sites existed and only one clamped. It truncates on a character
  boundary and says `… (truncated)`, because a reader wants the prefix where an error message wants a
  generic replacement. `every_control_attribute_is_bounded_at_construction` and
  `a_bounded_value_is_still_valid_utf8` are the pins.
- **A behavioural signal test needs TWO targets, or it proves the wrong thing.**
  `Collector::control` returns at the acceptance union before any lane filter runs, so a single-target
  test passes even when two signals share a severity — measured, with a control record landing in a
  verdicts-only file as `severityNumber 9`. `a_target_naming_only_verdicts_receives_no_control_record`
  declares a second target for exactly this reason.
- **The four-level ladder is gone, and its one `>=` is why.** `Level::admits` shipped inverted, so the
  default target received nothing and every box recorded no decision. A target now names a **set** of
  `Signal`s and membership has nothing to invert. `debug` was also a dead rung — no record was ever
  produced at it — and `trace` was a signal wearing a depth's clothing.
- **A wrapping `LogProcessor` must forward `set_resource`.** The trait's default is a no-op, so
  `TargetLane` swallowed it and every record shipped with `resource.attributes` empty: no record named
  its box or its producer. `the_records_carry_their_provenance` is the pin.
- **`Zeroizing` does not redact `Debug`.** It wipes memory on drop and prints the value. Since
  `LogExporter: Debug`, holding the value unwrapped put the vendor key on the SDK's diagnostic path.
  `Wire::Otlp` holds a whole `TargetSecret`, whose own `Debug` names the header and never the value, so
  the derive is safe. `an_exporters_debug_output_holds_no_secret` is the pin, and it failed before.
- **`dropped` counts a failed BATCH, and a full queue not at all.** Every transport failure passes
  through `TargetExporter::deliver`, which bumps the counter; before that, 50 records aimed at a
  closed port reported zero. What it still cannot see is the SDK's own queue: `dropped_logs_count` is
  private and reported only through `otel_warn!`, and **no `tracing` subscriber is installed anywhere
  in this workspace**, so a full-queue drop is not counted, not printed and not observable. That is
  why the counter is not on the facade. See
  [delivery is best effort](../../docs/design/decisions.md#delivery-is-best-effort).
- **`BODY_LIMIT` is the library's cap now, and the hand-rolled reader is why it needs to be.** That
  reader sized its buffer from the declared `Content-Length` before a byte arrived, so 64 connections
  could pin 256 MiB in the box's trusted process. `a_body_over_the_cap_is_refused` is the pin.
- **The stamp is a 4x memory amplifier, and `RESOURCE_LIMIT` is what bounds it.** Measured on a
  4 MiB body of two-byte empty `ResourceSpans` — 2,097,148 entries, which is inside `BODY_LIMIT`:
  the decode alone peaks at **230 MB**, and the decode plus `strip_and_stamp_resource` at **937 MB**,
  because the stamp pushes heap-allocated attributes into every entry. The extra 707 MB is this crate's,
  not the library's, and the workload triggers it at will against the process holding the CA private
  key. The permit is therefore taken **before** the decode, and
  `a_body_naming_too_many_resources_is_refused_on_every_route` pins the bound. The operator's
  `OTEL_RESOURCE_ATTRIBUTES` adds to every stamped entry, so `RESOURCE_ATTRIBUTES_LIMIT` caps it at
  1024 bytes, and `an_operator_attribute_value_over_the_bound_refuses` pins the cap. The stamp's peak
  with the cap reached is not measured. Do not move the permit
  back below the decode, and do not raise the limit without re-measuring.
- **`RELAY_CAPACITY` is 1, and 64 was wrong.** A file target's `Mutex<tokio::fs::File>` is held across
  `write_all` and `sync_all`, and the same `Arc<TargetExporter>` serves the SDK lane and the relay
  list. So 64 concurrent relays each doing a write and an `fsync` stalled the box's own export worker,
  and the SDK's queue overflow is not counted anywhere — which reopens exactly the audit-suppression
  hole that
  [the lane split](../../docs/design/decisions.md#the-agents-lane-and-the-boxs-lane-share-no-queue)
  claims is closed. One permit means the box's worker waits for at most one relay.
  **`a_flood_of_relayed_payloads_loses_no_decision` is the pin**, and it was the property's first one:
  200 concurrent posts land while 200 decisions are submitted, and every decision must reach the file.
  Its scope is the relay path, because the decision count stays inside the queue's own capacity — so it
  pins that a flood costs no decision, and **not** that the queue can never overflow. A test for the
  overflow case would have to raise the decision count above `max_queue_size`, which this crate does
  not configure, so it takes the library default.
- **`Collector::start` must stay synchronous, so the listener is bound with `std::net`.** A
  `block_on` inside a running runtime panics, and the box opens its collector beside its other
  mechanisms rather than at an `await`. The listener is set non-blocking and converted with
  `TcpListener::from_std` inside the serving task.
- **A probe of the workload's environment must not go through the `zsh` alias.** That alias reaches
  the hosted Shell, which has its own synthesized environment, so `zsh -c 'env'` reports the Shell's.
  Two end-to-end tests were written wrong this way before anyone noticed.
- **The workload can exec only itself.** A test probe cannot call `env`, `head`, or `curl` inside the
  box — the profile grants one exec literal. Use bash builtins and `/dev/tcp`.
- **Stamping a resource is not enough to stop forgery.** A decision record carries its verdict on the
  **record**, so a payload claiming `strands.box.source = "box"` deeper down read as a permit. The
  strip is a typed walk over every level a span carries. **Do not replace it with an untyped
  `serde_json::Value` walk** — that is the version that missed a level, and a walk searching for keys
  named `attributes` cannot be shown exhaustive.
- **`RESERVED_PREFIX` is `strands.box.`, and the box key names are part of that decision.** The
  product and the namespace share a word: the Strands Agents SDK owns `strands.cancellation.type` and
  `strands.tool.backgrounded`, and a reserve of `strands.` deletes both and still answers `200`. So
  the reserve narrows, and **all sixteen box keys moved under it in the same change** —
  `strands.policy.*` → `strands.box.policy.*`, `strands.control.*` → `strands.box.control.*`,
  `strands.trace.*` → `strands.box.trace.*`, `strands.request.id` → `strands.box.request.id`.
  **2026-09-25 finished the job**: `security_rule.name`, `.category`, and `.description` became
  `strands.box.policy.rule`, `.category`, and `.description`, so no box key sits outside the reserve
  under any spelling. The same change removed `security_rule.uuid`,
  `strands.box.policy.determining.tokens`, `strands.box.trace.correlation`,
  `strands.box.trace.link_traceparent`, and the four Deprecated `gen_ai.*`/`mcp.*` correlation keys.
  `link_traceparent` went because it was never emitted: it needs two valid, different parents on one
  MCP frame, and every capture on the author's machine held zero. `PROTOCOL_VERSION` moved to 6,
  because `Correlation` is `deny_unknown_fields` and an older alias naming a removed field is now
  refused rather than ignored.

  **Never move one half without the other.** The reserve is a prefix match, so narrowing it while a
  box key sits outside `strands.box.` makes that key forgeable: a harness payload claiming
  `strands.policy.verdict` would reach a target beside a real decision. Measured 2026-09-25 —
  narrowing the prefix alone fails all three
  `every_reserved_attribute_is_stripped_at_every_level_a_*_carries` tests, on all three routes.
  `a_strands_sdk_attribute_outside_the_box_namespace_survives` pins the other direction: the SDK's two
  names survive while a claimed `strands.box.policy.verdict` is still stripped.

  The authority is the attribute contract, *"Strands Box policy decision span and log"*, which states
  it as **"The box writes only `strands.box.*`, and nothing else under `strands.`."** That contract
  excluded the SDK's fourteen `strands.*` **metric instrument** names on the ground that the box
  served `/v1/traces` alone. The box now serves all three routes, so that exclusion no longer holds
  and the narrow reserve matters more, not less.
- **The box's own resource attribute order is NOT stable between batches, so no assertion may depend
  on it.** The SDK merges its resource with this crate's, and two batches in one run came out in
  different orders — one leading with `strands.box.name`, the next with `telemetry.sdk.name`. A
  shipped example asserted a refusal-only target held no agent log by matching the JSON substring
  `"resourceLogs":[{"resource":{"attributes":[{"key":"service.name"`, which passed by luck and then
  failed by luck. **Assert on `strands.box.source` instead**, which is what provenance actually means.
- **The receiver serves three routes, and `strip_and_stamp_resource` is ONE function for a reason.**
  Splitting the per-payload walk across three handlers is what introduced the defect: the first draft
  stripped each scope and each record but not the RESOURCE, so an agent's
  `strands.box.name = "box"` survived on the resource of every relayed payload, on all three routes.
  The strip and the stamp are now one call, and the order inside it is load-bearing — the stamp is
  itself in the reserved namespace, so a strip *after* it would delete the box's own provenance.
  The three `every_reserved_attribute_is_stripped_at_every_level_a_*_carries` tests are the pins, and
  each posts through the real route rather than calling a private function, because a unit test of one
  walk cannot see a route that forgot to call it.
- **The metric walk has three levels below the resource, and `match`ing `metric.data` exhaustively is
  what keeps them.** A metric carries reserved attributes in `metadata`, on each data point, and in
  each data point's `filtered_attributes` exemplar. Five data variants each hold their own point type,
  so a `_` arm here would silently skip one. `Summary` has no exemplars, which is the schema's
  asymmetry rather than an omission.
- **Every route applies the fan-out bound, and the second and third routes had to be told.** The
  measured 937 MB amplification is the stamp pushing three heap attributes into every resource entry,
  so a handler that decodes 1,025 empty `ResourceLogs` and stamps them costs the same as the trace
  case. `beyond_the_fan_out_bound` is the one owner, and
  `a_body_naming_too_many_resources_is_refused_on_every_route` walks all three.
- **`agent_logs` and `agent_metrics` took `Trace2` and `Trace3`**, because severity must stay unique
  per signal even for a relayed one. A relayed signal never reaches `TargetLane::emit`, so the value
  is unobservable in production — which is exactly why it is easy to give two of them the same
  severity and pass every behavioural test. `no_two_signals_share_a_severity` is the guard.
- **A file target's line must be one write.** `tokio::fs::File` caps a write syscall, so a very long
  line becomes several appends. One writer is safe; two boxes sharing one destination can tear a
  line. Prefer one target per box.
- **A telemetry secret must resolve through `credentials`.** `box`'s `telemetry_config` once read the
  variable with `std::env::var`, which bypassed the `env://` denylist — so
  `secret.ref = "secret://AWS_SECRET_ACCESS_KEY"` shipped the operator's AWS key to a vendor.
  `four_inputs.rs` pins it.
- **No refusal echoes a secret reference.** The first version printed it, which is exactly wrong for
  the case the check exists to catch.
- **`url` parses the destination, never this crate.** A hand-rolled authority split disagreed with
  `reqwest` on four spellings. Two of them sent a vendor key in the clear to an attacker-named host:
  `http://localhost:4318@evil.com/`, and — after the first fix — `http://evil.com\@127.0.0.1/`, because
  `\` ends the authority for a special scheme while `rsplit('@')` read the loopback address. The other
  two were false refusals: `127.0.0.2` is loopback, and the host is case-insensitive.
  `userinfo_cannot_forge_a_loopback_destination` pins the first class and
  `a_plain_loopback_destination_still_takes_a_secret` the second.

## Public surface

Fifteen names — `Collector`, `Target`, `TargetKind`, `TargetSecret`, `TelemetryConfig`, `Result`,
`TelemetryError`, `DecisionRecord`, `DecisionCause`, `DeterminingPolicy`, `Subject`, `Correlation`,
`ControlRecord`, `ControlOperation`, `Signal` — reached through `telemetry::open`, then:

**Three of those carry one decision's context, and each exists because a caller holds the value and
this crate must not re-derive it.** `Correlation` is the request's W3C parent, the transport request
identifier, and the JSON-RPC identifier of one MCP message — nothing else, since 2026-09-25.
`DeterminingPolicy` is one policy's identifier and its authored description, and the **first** one in
the list governs, so it supplies `strands.box.policy.rule` and `strands.box.policy.description`.
**No durable token enters this crate**: `DeterminingPolicy::new` takes one argument, because
`security_rule.uuid` and `strands.box.policy.determining.tokens` were removed as keys nothing joins
on.

**Entry zero agrees with the decision's own rule by construction, not by guarantee, and this is a
stated limit rather than a property.** `policy`'s `dogwood.rs` *defines* the decision's `rule` as
`attribution.first()`, so the two always agree. But the upstream contract in
`dogwood-local-engine`'s `attribution.rs` is *"Each determining token appears once. Ordering is
unspecified."* So when a **permit** rests on more than one policy, which one reaches those three keys
can differ between runs. Two things bound the cost: a **deny** is single under deny-overrides, which
is the case a security review reads; and `strands.box.policy.determining.ids` carries every policy,
so nothing is lost.
**Do not sort or filter the list before passing it**, and do not reorder it in `box`'s `into_record`:
`strands.box.policy.rule` would then stop agreeing with the rule the engine says decided.

**A policy is named only when one decided.** `governing()` reads the cause, because the engine reaches
`<default-deny>` on an evaluator fault and **keeps a non-empty attribution**. Naming entry zero there
reported an authored policy as the governing rule for a deny that policy did not decide.
`a_fault_names_no_authored_policy_although_it_keeps_attribution` pins all four such causes. `Subject` is what the decision was about, under
the standard names — `server.address` and `server.port`, `http.request.method`, `file.path`, or
`process.command`/`process.command_args`/`process.working_directory`. **Do
not parse a resource string to fill a `Subject`.** The enforcement point already holds host, port, and
method apart; only `fs:*` needs no subject, because its resource *is* the approved path and the record
copies it unchanged.

- `Collector::record` never blocks, never fails and never awaits. Strands Box calls it from a policy
  enforcement point before the effect or refusal. A record no target's signal set accepts is not
  built at all.
- `Collector::control` is the same contract for the other plane. Strands Box calls it where the
  authority itself changes — a policy install, a schema install, discovery completing, a box starting
  or stopping. **Each operation also reaches a span**, under `strands-box.control`, named
  `control <operation>`, with the same span ID as its log record.
- `Collector::drained` is the SDK's `shutdown`, which exports what is queued before it stops, so it
  needs no separate flush. Call it before teardown. `DRAIN_DEADLINE` bounds the whole shutdown, and two
  compile-time asserts order the three deadlines:
  `REQUEST_DEADLINE` < `EXPORT_DEADLINE` < `DRAIN_DEADLINE`, so a flush can tell delivery from loss and
  the drain never cuts a flush that would have finished.
- **The SDK bounds no shutdown, so this crate must.**
  `BatchLogProcessor::shutdown_with_timeout` names its argument `_timeout`, never reads it, and calls
  `futures_executor::block_on` on a `oneshot` only the batch worker can answer
  (`opentelemetry_sdk` 0.32.1, `src/logs/log_processor_with_async_runtime.rs`). So every deadline the
  box passes down is discarded, and `EXPORT_DEADLINE` bounded nothing on this path.
  `shut_down_bounded` is where the bound lives, and
  `the_drain_returns_when_the_batch_worker_cannot_answer` is the pin.
- **`Drop` must start the shutdown off the runtime thread and WAIT FOR NOTHING.** Both halves are
  load-bearing, and each was wrong once.
  - `spawn_blocking` is wrong, because a tokio runtime **joins its blocking tasks while it shuts
    down** while the reply it waits for comes from an ordinary runtime task that can no longer be
    scheduled. A detached `std::thread` is joined by no runtime.
  - **Waiting is wrong, even bounded.** A dropping `Collector` may hold the very runtime thread the
    batch worker needs in order to answer, so a bounded wait there starves the worker and then
    spends the whole deadline. Measured: a 10-second `DRAIN_DEADLINE` waited in `Drop` took this
    crate's own suite from **0.33 s to 10.11 s**, because the existing tests drop a collector inside
    a running current-thread runtime. `drained` is the call that waits, and it is safe there because
    `spawn_blocking` puts the wait on the blocking pool while the runtime stays free to drive the
    worker.
- **The drain thread can stay blocked until the process ends, and that is accepted.**
  `shut_down_off_runtime` detaches a `std::thread` that blocks in `logs.shutdown()` for as long as the
  batch worker does not answer. Every caller runs at teardown, so a one-shot `strands-box run` exits
  and the kernel reclaims the thread. The one place it is visible is this crate's own suite:
  `the_drain_returns_when_the_batch_worker_cannot_answer` leaves one blocked thread in the shared test
  process. Do not join that thread, because a join is the wait `Drop` must not take.
- **A box hanging for ever on exit was OPEN from 2026-08-23 and is now closed.** Keep this entry: it
  records why two earlier attempts failed.

  **What was measured then.** `strands-box run -- /bin/echo hello` printed `hello`, kept no child
  process, and then sat for **25 minutes**. It happened twice, both times inside `box_project` under
  `cargo test --workspace`, and `SIGTERM` ended it, so it is a blocked wait rather than a spin. The
  sampled stack is `BatchLogProcessor::shutdown_with_timeout`, under `Collector as Drop::drop`, on a
  tokio blocking task.

  **Why the two earlier attempts could not work.** Neither bounded the wait, and the wait is
  unbounded in the SDK rather than in this crate.
  1. "Shut the provider down **once**, with a flag." `SdkLoggerProvider::shutdown_with_timeout`
     already guards itself with a `compare_exchange` on its own `is_shutdown` and answers
     `Err(AlreadyShutdown)` without touching a processor, so this de-duplicated a call that was
     already de-duplicated.
  2. "Run the `Drop` shutdown on a detached `std::thread`." Necessary and not sufficient: the thread
     still waited for ever, because nothing bounded it.

  **What closed it.** The bound moved above the SDK, and `Drop` stopped waiting at all.
  `the_drain_returns_when_the_batch_worker_cannot_answer` reproduces the unschedulable worker below
  the box level, which the earlier attempts could not do. Measured after: 20 consecutive
  `strands-box run` invocations exited at a mean of **609 ms** and a worst of **665 ms**, with every
  `box_stopped` record present and no orphan process, and four consecutive `box_project` runs passed
  in 8 to 12 seconds with no slow-test warning.

  **The residual.** `DRAIN_DEADLINE` is one bound over every lane, and the SDK flushes lanes in
  sequence, so three or more unreachable OTLP targets can still reach the deadline and lose what the
  last lane held. Flushing lanes concurrently is the fix for that and is not done here.
- `Collector::port` is the loopback port the agent exports to.
- Every refusal happens in `open`. After it returns, no target failure reaches a request path.
